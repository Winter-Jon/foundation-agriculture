# Decisions — 2026-W37 (0907–0913)

## 2026-09-10 15:56:03 CST - Classify ambiguous upstream delivery as pending retry work

Tags: micu, retry, delivery, e2

### Decision

Micu `unknown_delivery`, malformed/truncated provider responses, and persisted
intents without a result are recorded as `retry_pending`, not as image/content
quality failures. The original ledger, request ID, error type, and latency remain
immutable lineage.

`retry_pending` does not authorize automatic replay. A retry must run in a
separately versioned batch with a new attempt and request ID after delivery-state
reconciliation when available. Public-boundary contaminated samples remain
`quarantined_no_retry`.

### Evidence and implementation

- E2 parent ledgers currently contain 65 `unknown_delivery` results, all typed
  `UnknownTeacherDelivery`; most parent failures occur after long waits.
- `scripts/report/audit_micu_classifier_hcv_e2.py` now emits a structured
  `retry_pending.jsonl` sidecar and separates retry work from quality verdicts.
- `tests/test_micu_classifier_hcv_e2_audit.py` verifies no automatic replay and
  permanent quarantine of boundary-leaked samples.

### Next

Finish the current no-replay derivation run, generate the retry sidecar and final
audit, then design any actual retry batch separately. Do not use retry rows for
SFT or acceptance statistics before successful re-audit.
