# Plans - 2026-W24 (0608-0614)

## 2026-06-13 17:34:49 CST - RAG tool-call distillation plan for AgriNet fine-grained recognition

### Goal
Build a YUNWU-based teacher data generation pipeline that teaches a multimodal LLM to call the deployed AgriNet Milvus RAG service as tools. The target behavior is: given an agricultural query image, the model generates search queries and retrieval hyperparameters, calls different RAG retrieval modes, compares visual evidence, wiki evidence, and similar-class evidence, repeats search when evidence is weak, and outputs a conservative final class decision with uncertainty.

### Current Basis
- Milvus search service is deployed through `src/agrinet/rag/milvus_tools/search_api.py`, intended at `http://127.0.0.1:8077`.
- Collection `agrinet_wiki_siglip2` contains 320 wiki-backed class rows from `datasets/AgriNet-1K/wiki/base.json`.
- Existing retrieval channels are dense text, dense image, and sparse class-name/alias vectors.
- Existing API presets are `balanced`, `visual`, `semantic`, `name`, and `rrf`, with request-level overrides for `top_k`, `ranker`, `text_weight`, `image_weight`, and `sparse_weight`.
- Existing teacher collection code already uses YUNWU / OpenAI-compatible endpoints through VLooM adapters under `src/agrinet/data/vloom_tools/`.
- ms-swift Agent data format requires `tools` as a JSON string; tool calls use `messages[].role = "tool_call"`; tool outputs use `messages[].role = "tool_response"`; tool call and response content must be JSON strings.

### Tool Design
1. Define one high-level tool named `agrinet_rag_search` rather than exposing each HTTP route as a separate model-visible tool. This keeps the action space compact while still letting the model choose retrieval mode and hyperparameters.
2. Tool arguments should include:
   - `query`: natural-language search text generated by the model.
   - `retrieval_type`: one of `balanced`, `visual`, `semantic`, `name`, or `rrf`.
   - `image`: enum such as `query_image`, `none`, or a future crop/reference handle; first version uses only `query_image` or `none`.
   - `top_k`: integer, default 5, bounded to a small range such as 1-10.
   - `ranker`: `weighted` or `rrf`.
   - `text_weight`, `image_weight`, `sparse_weight`: optional overrides for the three retrieval signals.
   - `filter`: optional Milvus expression for class-domain constraints when known.
   - `rationale`: short model-side reason for this search, useful for rejection sampling audits.
3. Tool responses should return compact evidence, not raw full records: class code, English/Chinese names, aliases, score/distance, image path(s), wiki summary fields, and evidence fields needed for contrastive reasoning.
4. Keep the HTTP implementation as a backend adapter. The student only sees the abstract `agrinet_rag_search` schema, not server paths or internal Milvus details.

### Data Generation Steps
1. Build a small tool schema module that exports the ms-swift-compatible `tools` JSON for `agrinet_rag_search`.
2. Implement a teacher runner that sends the query image and tool schema to the YUNWU teacher model, asks it to produce an initial `tool_call`, executes the call against `src/agrinet/rag/milvus_tools/search_api.py`, appends a `tool_response`, and allows another reasoning/tool-call turn.
3. Use a multi-turn cap, for example 3 retrieval rounds. The teacher should search again when the top results disagree, when wiki evidence is generic, when similar classes remain visually close, or when confidence is below threshold.
4. Construct each final sample in ms-swift format:
   - `tools`: JSON string containing `agrinet_rag_search` schema.
   - `messages`: user image question, assistant/tool_call turns, tool_response turns, and final assistant answer.
   - `images`: query image path only, unless a later experiment intentionally exposes retrieved reference images as additional images.
5. Preserve hidden collection artifacts separately: full retrieval JSON, raw YUNWU responses, parse/repair logs, selected/rejected sample reasons, token usage, and tool latency.

### Reasoning Target
1. The assistant should first form one or more search hypotheses from the image: object type, visible morphology, disease symptoms, likely host, color/shape/pattern, and uncertain alternatives.
2. It should call different retrieval categories according to need:
   - `visual`: when image appearance is the primary signal or when no good class name is known.
   - `semantic`: when symptoms, morphology, host, ecological role, or natural-language descriptions are useful.
   - `name`: when the model has a candidate class/code/name and needs exact alias lookup.
   - `balanced` or `rrf`: when combining image and text evidence or when score scales look unstable.
3. After each tool response, the assistant should contrast the retrieved candidates using visual traits, wiki descriptions, aliases, and similar-class differences.
4. The final answer should include the predicted class, evidence summary, rejected alternatives, uncertainty, and a refusal/insufficient-evidence path when the retrieved candidates are still weak.

### Rejection Sampling
1. Sample multiple YUNWU trajectories per image with varied temperature, top-k, and retrieval presets.
2. Accept a trajectory only if:
   - all tool calls parse as valid JSON and match the schema;
   - at least one tool call is made for nontrivial classification samples;
   - final label is in the candidate/retrieved class set or explicitly marked insufficient;
   - final label matches ground truth when the sample has a known AgriNet class;
   - reasoning references actual retrieved evidence and does not invent unavailable wiki facts;
   - repeated searches are used when the first evidence set is ambiguous.
3. Reject or down-rank trajectories with malformed tool calls, unsupported parameters, hallucinated classes, direct leakage of ground truth without evidence, overconfident wrong labels, or superficial one-shot reasoning.
4. Store accepted SFT samples and rejected alternatives so the same collection can later support DPO/ORPO or reward-model experiments.

### Implementation Milestones
1. Add `src/agrinet/rag/distill/` or `src/agrinet/data/vloom_tools/rag_tool_distill/` with tool schema, API client, turn executor, validator, and converter to ms-swift JSONL.
2. Add a small smoke dataset from known AgriNet wiki-backed classes and run 5-10 samples through dry-run mode using mocked tool responses.
3. Run a real YUNWU pilot with low concurrency, for example 20-50 samples, and measure parse success, tool-call validity, retrieval depth, and label accuracy.
4. Add rejection-sampling filters and regenerate a cleaner pilot set.
5. Scale to disease/pest or another high-value subset first, then broaden to all wiki-backed classes.
6. Train a small ms-swift agent SFT run using `agent_template` such as `hermes` or a Qwen-compatible default, then evaluate tool-call validity and classification accuracy against a held-out set.

### Acceptance
- A validated ms-swift JSONL file exists with tool-call trajectories using `agrinet_rag_search`.
- Each accepted sample has valid `tools`, `messages`, and `images` fields and passes schema validation.
- Tool calls exercise at least the three important retrieval signals: visual/image, semantic/wiki text, and name/sparse lookup.
- Multi-turn samples are present for ambiguous cases, with repeated retrieval driven by explicit uncertainty or candidate conflict.
- Pilot evaluation reports tool-call parse rate, successful API-call rate, accepted/rejected counts, final-label accuracy, average retrieval turns, and common rejection reasons.

### Distilled Artifact Design
The final distillation output should be a versioned artifact directory, not a single JSONL file. The training JSONL should contain only student-visible information, while full teacher traces and rejection-sampling metadata should remain in sidecar files for audit, filtering, and future preference training.

Recommended layout:

```text
outputs/rag_distill/agrinet_rag_toolcall_v1/
  README.md
  manifest.json
  tools/agrinet_rag_search.schema.json
  train/agent_sft.accepted.jsonl
  train/agent_sft.accepted.compact.jsonl
  preference/dpo_pairs.jsonl
  eval/heldout_agent_eval.jsonl
  traces/raw_trajectories.jsonl
  traces/retrieval_calls.jsonl
  traces/rejected_trajectories.jsonl
  reports/validation_summary.json
  reports/validation_summary.md
  reports/rejection_reasons.csv
```

Required files:

1. `manifest.json` records artifact version, creation time, source dataset, git commit if available, teacher model, YUNWU endpoint name without credentials, Milvus collection, embedding model, RAG API route version, prompt version, sampling settings, acceptance policy version, and counts.
2. `tools/agrinet_rag_search.schema.json` stores the exact tool schema used in `tools`, including argument descriptions and enum values.
3. `train/agent_sft.accepted.jsonl` is the canonical ms-swift Agent SFT file. Each line is a complete training sample with `tools`, `messages`, and `images`.
4. `train/agent_sft.accepted.compact.jsonl` is an optional smaller version where verbose tool responses are truncated to top evidence fields, for sequence-length-limited SFT.
5. `traces/raw_trajectories.jsonl` stores full teacher conversations, raw YUNWU responses, parser repair logs, and full retrieval payloads. It is not used directly for SFT.
6. `traces/retrieval_calls.jsonl` is a flat call ledger: one row per tool call, useful for checking retrieval mode distribution and latency.
7. `traces/rejected_trajectories.jsonl` stores rejected samples with rejection reason codes and enough metadata to reproduce the decision.
8. `preference/dpo_pairs.jsonl` stores optional accepted-vs-rejected pairs sharing the same input image/question for later DPO/ORPO experiments.
9. `eval/heldout_agent_eval.jsonl` stores held-out tool-call evaluation samples with labels and expected evidence constraints, not used for training.
10. `reports/validation_summary.*` summarizes parse success, tool-call validity, accepted/rejected counts, final-label accuracy, average retrieval turns, retrieval-type distribution, and top rejection reasons.

Student-visible constraints:

1. `images` should contain only the query image in the first version.
2. Tool responses may include retrieved reference image paths as metadata only if needed for audit, but should not add retrieved images to the student `images` list unless the experiment intentionally trains image-reference comparison.
3. The final assistant answer should be evidence-grounded and concise; raw teacher chain-of-thought can stay in `traces/raw_trajectories.jsonl` and should not be blindly copied into the SFT file.
4. Ground-truth labels can appear in `metadata`, but the user prompt must not leak the answer.
5. Tool responses must be compact enough to fit the target context length and should include only fields the model can legitimately use: class code/name, aliases, score, wiki evidence summary, candidate image metadata, and similar-class notes.

Minimum quality gates before marking an artifact release-ready:

1. 100% JSONL parse success for accepted SFT samples.
2. 100% valid `tools` JSON string and valid `tool_call` / `tool_response` JSON strings.
3. 100% tool calls conform to the `agrinet_rag_search` schema and allowed enum/range values.
4. At least 95% successful backend retrieval calls, excluding intentionally simulated insufficient-evidence cases.
5. Reported final-label accuracy against known ground truth, plus separate rates for insufficient-evidence decisions.
6. Retrieval coverage report showing use of visual, semantic, and name/sparse signals; avoid a degenerate dataset where every accepted sample uses only one preset.
7. Leakage check confirming the prompt does not expose ground-truth labels and student `images` does not include unintended retrieved reference images.
8. Reproducibility check confirming `manifest.json` can identify the exact prompt, tool schema, RAG service, collection, and acceptance rules used to generate the artifact.

### Risks
- Milvus Lite can lock the DB if multiple clients access the same file; prefer a single resident API service and avoid concurrent CLI search against the Lite DB during collection.
- Retrieved reference images may leak strong answer cues if exposed directly to the student. First version should expose retrieved image metadata/evidence text through tool responses and keep only the query image in `images`.
- The current image embedding uses the first local reference image per class, which may underrepresent visually diverse classes.
- Teacher traces may contain unverifiable chain-of-thought. Store raw traces for audit, but convert training data to concise, evidence-grounded assistant reasoning compatible with the intended training policy.
- YUNWU rate limits or provider instability may require lower `MAX_CONCURRENT`, retries, and deterministic resumption.
