## 2026-08-15 14:25:00 CST - Prevent automatic replay after ambiguous teacher POST delivery

### Context

Round116 showed that a teacher request can remain unresolved after the local timeout. Replaying such a POST can duplicate provider work or create an untraceable second delivery.

### Changes

- Added `UnknownTeacherDelivery` to the local Pilot runner. Empty/invalid POST bodies, `URLError`, socket failures, and direct timeouts are classified as ambiguous delivery.
- HTTP 408, 429, and 5xx responses from the teacher POST are also fail-closed as ambiguous delivery; deterministic 4xx request errors remain ordinary failures.
- `post_teacher_json` now raises immediately for that class and never consumes the configured transient retry budget.
- A sample records `unknown_delivery` with `delivery_status=unknown`; a batch manifest records `counts.unknown_delivery` and `delivery_status=unknown`, and exits with code 2 when such a row occurs.
- Existing strict validators and acceptance gates were not relaxed.

### Validation

- `py_compile` and targeted `git diff --check` passed.
- No teacher request, Pilot, SFT, or evaluation was started during this change.
